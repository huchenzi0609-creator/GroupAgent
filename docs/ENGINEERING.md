# 开发流程与纪律草案

状态：Spec v0.1 Draft的工程流程基线，2026年11月13日。当前仅建立本地Git和文档；远程分支保护、CI、监控与发布系统尚未配置。

## 1 阶段边界

本轮交付初版spec、契约和计划，不修改旧机器人运行代码、不更新生产服务、不迁移群数据。正式实现以用户确认的spec及后续授权为准。

后续每项工作通过以下路径推进：

1. 需求：说明用户场景、当前问题、目标行为和不在范围内的内容。
2. 验证：对依赖、接口、模型行为和资源上限做最小实验，记录失败证据。
3. 规格：确定数据契约、状态转换、权限、预算、错误语义和验收样例。
4. 设计：跨模块或难逆转的取舍形成ADR，说明方案、替代方案、代价和重新评估条件。
5. 实现：在独立分支完成一项可审阅目标，提交代码、必要测试和说明。
6. 审查：审阅最终diff和证据；不能用“模型说没问题”替代检查。
7. 验收：测试环境与测试群验证产物、权限和故障恢复。
8. 发布：同一构建产物灰度进入生产，有回滚入口和观测指标。
9. 复盘：问题转为回归样例，更新规范，不靠记住一次口头提醒。

## 2 需求与变更管理

- 每项需求给出稳定ID，如CHAT-001、MEDIA-001、EXEC-001；代码、测试与发布说明引用它。
- 一个issue至少包含触发场景、预期行为、验收办法、依赖与可观测的完成定义。
- 需求不清时询问阻塞项；可以先完成不依赖答案的研究或隔离实验。
- 变更范围扩大时更新issue与PR描述，不把旧方案作为当前设计。
- 实验性实现与生产路径用明确配置隔离，不在群内偷偷启用未验收功能。

## 3 Git与审查

- main用于稳定基线；feat/*、fix/*、docs/*承载短期工作；试验可用spike/*，结果应归档或移除。
- 初始仓库bootstrap可直接提交；之后以PR合并为正式团队流程。当前本地报告分支不假装已经有远程PR。
- 提交应聚焦，描述实际变化；禁止夹带运行数据库、密钥或无关格式化。
- 上游fork保留upstream，补丁有编号、原因、测试及上游同步状态。优先以扩展接口替代深改。
- 发布打版本标签并记录构建清单；不使用浮动latest作为唯一生产标识。
- 禁止向共享分支强推、改写已经发布的历史或未评审直接覆盖生产代码。
- 后续远程仓库应设置main禁止直接推送、必需检查、至少一名适当审阅者及过期批准失效。单人项目可采用明确的人工发布复核，不能伪造第二审阅人。
- 紧急修复也必须有对应提交、验证、部署记录和事后复盘。

## 4 CI与质量门槛

实施阶段应落地，而非仅写在文档中的流水线：

| 检查 | 目的 | 何时必须 |
| --- | --- | --- |
| 格式、lint、类型、构建 | 提前发现确定性缺陷 | 代码PR |
| 单元与属性测试 | 状态转换、身份、时间、去重、预算等不变量 | 相关模块变更 |
| Adapter/Engine/Tool契约 | 供应商或框架升级不破坏边界 | 适配器、插件、模型配置升级 |
| 数据库迁移与恢复 | 旧数据可读取、备份可恢复、失败可停住 | schema或存储变更 |
| Agent离线评估 | 行为不因提示词或模型变化退化 | 提示词、模型、参与策略变化 |
| 文件结构与渲染检查 | 内容修改与实际文件结果一致 | 文档或图片工具变化 |
| 故障注入 | 断网、崩溃、超时、撤销、取消不会重复外部操作 | 关键执行和投递变化 |
| 秘密、依赖、许可扫描 | 避免凭证泄露和未评估供应链变化 | 所有PR及发布 |
| 端到端测试群验收 | 验证真实媒体、发送及客户端显示 | 首次接入、版本升级、发版前 |

测试不追求数量本身；围绕失败模式与业务不变量。可逆、低影响文档编辑不要求新增镜像实现的形式化测试。报告必须区分mock、容器、模拟时钟与真实微信测试。

模型评估固定样本版本、模型路由、推理设置、工具版本与评分办法；可重复运行并保存失败轨迹。LLM裁判只能作为辅助，关键样例有人审查。模型输出不是审批记录或执行成功证明。

## 5 数据与敏感信息

- 代码仓库只放代码、公开文档、配置样例和合成／授权脱敏fixture。
- 实际消息、成员ID、文件、数据库、二维码、会话凭证、私钥和API密钥放在受控运行存储，不入Git，不进入构建上下文。
- 配置分为非秘密配置、密钥、群策略和个人偏好；有独立的版本或审计记录。
- 微信接入凭证属于channel进程；执行worker不能读取客户端profile或其他群缓存。
- 迁移先保留原件与备份，验证新系统，再做单一生产发送者切换；不同时启用两个能回复同一群的实例。
- 删除请求应考虑原文、检索索引、摘要、产物和备份保留策略，不能只删除模型当前上下文。

## 6 执行与插件纪律

- 所有模型发起的动作经统一工具网关，不允许直接获得生产Shell、数据库管理员或Docker socket。
- 工具定义包含输入输出schema、允许角色、资源范围、超时、最大产物大小、幂等和审计字段。
- 默认低风险工作自动执行，只有信息不足、超出已授权范围或高影响动作需要澄清／审批。
- 网页、文件、OCR和群内引用文本均视为不可信数据；不能借此改变权限或部署配置。
- 插件安装与升级经过固定版本、许可及数据流检查。禁止Agent运行时自主安装任意插件或自改生产权限。
- 开发使用的Agent能力和最终产品对群成员开放的能力是两个权限域，不能相互继承。

## 7 发布与运维

每次发布清单至少记录：应用commit、镜像digest、Harness及接入客户端版本、依赖锁、模型与提示词版本、schema版本、迁移步骤、配置摘要、验收证据、回滚目标。

发布顺序：备份并验证恢复 → 测试环境 → 回放／shadow → 测试群 → 小范围真实执行 → 生产。数据迁移和对外副作用分别管理；旧版本二进制能启动不代表能读取新schema。

监控最低集：接入在线与重新认证状态、事件延迟、队列长度、工作单成功率、工具失败率、发送不确定项、重复发送、产物验证失败、模型与工具费用、内存和磁盘。

重试按错误分类：短暂网络故障有退避与上限；权限错误停止相关工作；不确定副作用先查询回执；永久失败进入待处理队列，不反复占用整个群服务。

维护连接采用最小权限和有审计的访问方式。临时维护授权到期后失效并清理；不能把机器人运行依赖于持续保留管理员个人登录。

## 8 Done定义

一个功能完成必须同时满足：需求与文档更新、必要自动检查通过、相应真实链路验收、失败与取消行为明确、监控和费用可见、迁移及回退可执行、没有未说明的关键限制。

文档报告的完成定义不同：结论有证据，假设与事实分开，所引用的版本可定位，未验证部分明确，文件与Git状态可复核。不得将本轮文档完成汇报成新版产品上线。
